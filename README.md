# shoplist-crawler

Yahoo!ショッピングの各店舗の「会社概要」ページ
(`https://store.shopping.yahoo.co.jp/<店舗ID>/info.html`) の情報を集める個人用ツールです。

クローラーは次の3種類です。

| | 役割 | コマンド | 動く条件 |
|---|---|---|---|
| ① 新店舗の発見 | カテゴリー×価格帯で商品検索し、店舗IDを集める(粗い価格帯を全カテゴリーで一巡 → 細かい価格帯へ) | `collect-categories` | 初回に全体を検索。以後は `--recrawl-days`(既定30日)より古い検索をやり直す |
| ② 新店舗の情報取得 | まだ会社概要を取得していない店舗を取得する | `fetch` | 未取得の店舗がある間 |
| ③ 既存店舗の情報更新 | 取得から日数が経った店舗を取り直し、変更・閉店を記録する | `refresh` | 取得から `--older-than-days`(既定30日)が経った店舗 |

①で見つけた店舗が②で取得され、③が定期的に取り直します。出力は `export`(CSV)、`changes`(変更履歴)です。

`info.html` には `__NEXT_DATA__` というJSONが埋め込まれているので、HTMLの見た目ではなくそのJSONを読みます。
取得できる主な項目: ストア名/フリガナ/紹介文、評価、会社名、代表者、住所、運営責任者、電話/FAX/メール、営業時間、関連ストアURL。

## セットアップ

```bash
pip install -e '.[dev]'
```

Yahoo!デベロッパーネットワークでアプリケーションを登録し、Client ID(appid)を取得してください(無料)。

```bash
export YAHOO_APP_ID=取得したClientID
```

## 使い方

```bash
# 1. カテゴリーごとに店舗IDを集める(推奨)。デフォルトは 13457=ファッション の2階層目/3階層目
shoplist collect-categories --list-only      # まず対象カテゴリーの一覧だけ確認
shoplist collect-categories --estimate       # 各カテゴリーの商品件数を調べ、必要な時間を見積もる
shoplist collect-categories --max-minutes 60 # 実行。中断しても、再実行すると続きから再開
shoplist collect-categories --root-id 2498   # 別のトップ階層(例: 食品)

# キーワードで集めることもできる / 既にIDを知っている場合は手動で追加
shoplist collect --queries-file queries.example.txt --all-sorts   # 1検索あたり先頭999件まで
shoplist add-ids lafitte

# ② 新店舗の情報取得(Ctrl-Cで止めても、再実行で続きから)
shoplist fetch
shoplist fetch --limit 100          # 試しに100件だけ
shoplist fetch --retry-errors       # 前回エラーだった店舗をやり直す

# ③ 既存店舗の情報更新(取得から30日以上が経った店舗を、古い順に取り直す)
shoplist refresh --limit 500
shoplist refresh --older-than-days 10
shoplist changes --since-days 30    # 検出した変更の履歴(新しい順)。--out changes.csv でCSVに全件出力

# 出力 / 進捗確認 / 数件を表示
shoplist export --out shops.csv     # 下記の11列。店舗×カテゴリーごとに1行
shoplist export --format full --include-closed   # 全項目(1店舗1行)。状態・取得日時つき、閉店した店舗も含む
shoplist status                     # 件数の内訳と、直近30日の新規発見・変更・閉店
shoplist sample -n 5
```

#### ①②③の動き

- **① 新店舗の発見**: 検索の進捗は「カテゴリー×価格帯」ごとにDBに保存され、中断しても続きから再開します。
  `--recrawl-days`(既定30日)より古い進捗は検索し直すので、あとからできた店舗が見つかります(商品検索APIに新着順がないため、全体を見直す形で、時間がかかります)。`--recrawl-days 0` で無効にできます。
- **② 新店舗の情報取得**: `fetch` が未取得の店舗を取得します。エラーが20回続くと、アクセス制限などの可能性があるので止まります。
- **③ 既存店舗の情報更新**: `refresh` が取り直して、内容を前回と比べます。電話番号・住所・代表者などが変わっていれば `changes` に記録します
  (評価の点数・件数は頻繁に変わるので、変更とは見なしません)。
  - 取得できていた店舗が404になったら **`closed`(閉店・削除)** にします。最後に取れた内容は消さずに残し、`export --include-closed` で出せます。
  - 閉店した店舗が再びページを持ったら、`ok` に戻して「状態の変更」を記録します。
  - 取得に失敗した店舗は前回のデータを残し、次回また対象になります。
  - 閉店・不明の店舗の再確認は、営業中の店舗の4倍の間隔(既定120日)です。

### 出力するCSVの列

`URL, 会社名（商号）, 郵便番号, 住所, 代表者, ストア名, ストア名（フリガナ）, 運営責任者, お問い合わせ電話番号, お問い合わせメールアドレス, カテゴリー`

- `カテゴリー` は `メンズファッション/その他メンズファッション` のように「2階層目/3階層目」(トップの「ファッション」は省略)。
  1つの店舗が複数カテゴリーで見つかった場合は、カテゴリーごとに行を分けます。カテゴリーが不明な店舗(キーワード検索や手動追加)は空欄の1行です。
- `住所` はページの「お問い合わせ情報」の住所(建物名まで)です。`代表者` は日本語の姓名の間の空白を除いています(例: `伊藤憲博`)。
- 既定では、営業中(`ok`)の店舗だけ出力します。閉店を検出した店舗を含めるには `--include-closed` を付けてください。
- **取りこぼしを減らす仕組み**: 商品検索APIは1つの検索につき先頭999件までしか返しません。商品数が多いカテゴリーは、**価格帯で分割**して検索します
  (カテゴリー全体 → 0〜499円, 500〜999円, … → それでも999件を超える価格帯は半分ずつ)。各検索が999件に収まるまで割るので、
  カテゴリー内の全商品、つまり全店舗に届きます。同じ価格の商品が999件を超える場合だけ、並び順を変えて取れるだけ取ります。
  代わりにリクエスト数が増えます。`--estimate` で見積もってから実行してください。
- 進捗(どのカテゴリー×価格帯まで終わったか)はDBに保存され、中断しても続きから再開します。

データは `shops.db`(SQLite)に保存されます(`--db` で変更可)。`raw_json` に店舗情報の生データを保存しているので、
後から別の項目が欲しくなってもページを再取得する必要はありません。

## GitHub Actionsで動かす

`.github/workflows/crawl.yml` が、6時間おき(12:17 / 18:17 / 0:17 / 6:17 JST)と手動実行(Actions タブ → crawl → Run workflow)で動きます。

**初回設定**: リポジトリの Settings → Secrets and variables → Actions に2つ登録してください。

| Secret | 内容 |
|---|---|
| `YAHOO_APP_ID` | Yahoo!デベロッパーネットワークのClient ID |
| `DB_PASSPHRASE` | データ暗号化用のパスフレーズ(長いランダム文字列。控えを必ず保管) |

**流れ**: 前回のArtifactから `shops.db` を復元 → ② `fetch`(最大2時間) → ③ `refresh`(最大90分) → ① `collect-categories`(**残り時間をすべて使う**) → CSV・変更履歴を出力 → **暗号化して**Artifactに保存。
- ②と③は、やることがある分だけ動きます(未取得・更新対象の店舗がなくなれば、すぐ終わります)。
- ①は、ジョブの330分目まで使います。②③が空いた分の時間が、いちばん時間のかかる発見に回ります(②③が忙しい回は、最短で約100分)。
- GitHubホステッドランナーは1回のジョブが最長6時間なので、1回を伸ばすのではなく、実行回数(6時間おき=1日4回)で稼働時間を増やしています。
- 発見は、**まず全カテゴリーを粗い価格帯で一巡**し、そのあとで細かい価格帯へ進みます(1つのカテゴリーを掘り尽くしてから次へ行く方式より、新しい店舗が早く多く見つかります)。
- どのステップも進捗を保存して打ち切り、次回は続きから再開します。

手動実行の入力: `chain`(連続実行するか。既定 false)、`collect_minutes`(①に使う最大時間。実際は残り時間の範囲内。動作確認では5などに)、`root_id`(トップ階層のカテゴリID。既定13457=ファッション)、`limit`(②の最大件数)、`refresh_limit` / `refresh_days`(③の最大件数 / 何日経った店舗を対象にするか)、`recrawl_days`(①のやり直し間隔)。
収集に何日かかるかは、`shoplist collect-categories --estimate` の見積もりで確認してください。
1回の実行で取れる店舗数の目安(1店舗あたり約2.9秒): ② 約2,500店舗 / ③ 約1,900店舗。1日4回なら、③は30日で約23万店舗分あります。

**連続実行(自動で次の実行を起動)**: GitHub の cron は、遅れたり飛ばされたりします(実測で、1日4回の予定が1日1〜2回程度でした)。
そこで、定期実行(schedule)の最後に「やることが残っていれば、次の実行を自分で起動する」工程を入れています。次の実行は、同時実行の制限で、前の実行が終わるまで待機します。cron は予備として残しています。
- 次を起動するのは、**未取得の店舗がある**、または**発見が最後まで終わっていない**ときだけです。どちらも終わっていれば止まります。
- 次のときは起動しません: ②の取得が失敗した(アクセス制限など) / ①の発見が失敗した(429など。叩き続けないため) / アップロードに失敗した / 実行をキャンセルした。
- 手動実行は、入力の `chain` を `true` にしたときだけ連続実行します(動作確認の実行が、勝手に続かないように、既定は `false`)。
- **止めたいとき**: Actions の `crawl` で `Disable workflow` を押す。または、リポジトリの Settings → Secrets and variables → Actions → Variables に `CRAWL_CHAIN` = `false` を作る(実行中の分が終わったあと、連続実行だけが止まります)。
- 発見が終わって未取得もなくなれば、連続実行は自然に止まり、あとは cron(6時間おき)の定期実行だけになります。

**重要: このリポジトリはpublicです。** Artifactは誰でもダウンロードできるため、代表者名・メール・電話番号を含むDBとCSVは
`DB_PASSPHRASE` で暗号化したものだけを保存します。平文のデータはコミットもアップロードもしないでください。
`DB_PASSPHRASE` を失う、または変えると、過去のデータは復号できなくなります。

結果の取り出し(Actionsの実行ページ → Artifacts → `shops-data` をダウンロードして展開):

```bash
export DB_PASSPHRASE='設定したパスフレーズ'
scripts/crypt.sh dec shops.csv.enc shops.csv              # 指定の11列(営業中のみ)
scripts/crypt.sh dec shops_full.csv.enc shops_full.csv    # 全項目(状態・取得日時つき、閉店した店舗も含む)
scripts/crypt.sh dec changes.csv.enc changes.csv          # ③で検出した変更の履歴
```

DBを復号すれば、ランダムに数件を表示して中身を確認できます。

```bash
scripts/crypt.sh dec shops.db.enc shops.db
shoplist sample -n 5
```

注意:
- Artifactの保存期間は最大90日です。毎日の実行で毎回更新されるので消えませんが、90日以上実行が止まるとデータが失われます。
- publicリポジトリでは、60日間リポジトリへの活動がないとスケジュール実行が自動で無効になります。止まったらActionsタブから再有効化してください。
- GitHubのサーバーのIPからだと、Yahoo側にアクセスを弾かれる可能性があります。まず手動実行で、`limit` を小さく(例: 20)して試してください。

## ANA Mall(約250店舗)

Yahoo とは別のDB・別のワークフロー(`.github/workflows/anamall.yml`)で動かします。同時に動いても衝突しません。

```bash
shoplist --db anamall.db anamall-discover                 # ショップ一覧(1ページ)から店舗コードを集める
shoplist --db anamall.db fetch --site anamall --limit 5  # 店舗ガイドから会社情報を取得(10秒おき)
shoplist --db anamall.db refresh --site anamall --older-than-days 6   # 取り直して変更・閉店を記録
shoplist --db anamall.db export --site anamall --out anamall.csv       # Yahoo と同じ11列
```

- 取得元: ショップ一覧 `https://anamall.ana.co.jp/feature/shops.aspx` と、店舗ごとの `.../shop/shop/guide.aspx?shop=<4桁コード>`。
- 取れる項目: 販売事業者名、ショップ名、所在地(〒付き)、代表者、店舗運営責任者、電話・FAX・メール(「お問い合わせ先」欄に店舗が書いている場合)。
- フリガナはありません(空欄)。カテゴリーは、一覧ページに印がある「ANAグループ」の店舗だけ入ります(ほかは空欄)。
- **アクセス間隔は10秒**です。ANA Mall の `robots.txt` が、AI のクローラー向けに `Crawl-delay: 10` を求めているためです(私のクローラーの名乗りはその一覧にはありませんが、サイトの意図に合わせています)。
- ワークフローは、毎週土曜 18:37 UTC(日曜 3:37 JST)と手動実行で動きます。約250店舗で約45分です。結果は暗号化して、Artifact `anamall-data` に保存します(Yahoo と同じ `DB_PASSPHRASE`)。

## マナー・注意

- `fetch` はデフォルトで約2〜3秒間隔でアクセスします。`--delay` を短くしすぎないでください。429/5xxは自動で間隔を空けて再試行します。
- 商品検索APIのリクエスト間隔は既定で2秒です。回数制限(429)になった場合は、待ってから再試行し、それでも解けなければ集めた分を保存して中断します(時間を置いて再実行してください。制限の条件は公開されていません)。
- 代表者名・メール・電話番号が含まれます。個人利用の範囲にとどめ、再配布や営業メールの一斉送信などには使わないでください。
- Yahoo!ショッピング/Yahoo!デベロッパーネットワークの利用規約は各自で確認してください。
